# PRD-173 — Recoverable Workflow Errors and Failure Checkpoints

## Executive summary

When an agenthicc workflow encounters an error, the current execution can be
left without a usable checkpoint. In some cases the failure occurs before a
workflow handle or typed context exists. In others, the runner records a
terminal `failed` checkpoint even though the work could safely continue, or a
timeout bypasses workflow finalization altogether. Checkpoint-write errors are
also swallowed in several paths. The result is that the user sees an error,
but cannot restart the workflow from its last safe point.

This PRD defines a single, durable error-recovery contract. Every workflow
failure must be classified, persisted, surfaced, and either made resumable or
explicitly marked non-recoverable. Recoverable execution errors use the
existing `paused` lifecycle with a reason describing the error. A subsequent
`/workflow resume [run-id]`, `--resume`, or `--continue` must rehydrate the
same run, the same session conversation, and the last valid workflow context.

The contract applies to built-in workflows, custom workflows, and workflows
generated by `create_workflow`. Generated workflows must inherit the framework
error/checkpoint wrapper and must be taught to create a typed, serializable
context before their first failure-prone operation.

## 1. Evidence-backed current-state study

The investigation examined the current workflow ownership and persistence
boundary in:

- `src/agenthicc/runners/tui_session.py`
- `src/agenthicc/runners/workflow_handle.py`
- `src/agenthicc/runners/workflow_checkpoint_store.py`
- `src/agenthicc/runners/workflow_recovery.py`
- `src/agenthicc/workflows/checkpoint.py`
- `src/agenthicc/workflows/base_runner.py`
- the built-in runners under `src/agenthicc/workflows/`
- the workflow recovery, resume, TUI, integration, and E2E tests under
  `tests/`

PRD-170 already provides the durable checkpoint and resume foundation. This
PRD addresses the failure paths that still fall outside that foundation; it
does not replace PRD-170's ownership lease, conversation rehydration, or
tool-transaction repair contracts.

### 1.1 Failure points found

| Failure point | Current behaviour | Why the run cannot be restarted |
|---|---|---|
| Plugin `build_params()` | Called before a workflow handle is created | There is no run ID or checkpoint to recover |
| Handle claim/create | Can fail before the handle is assigned to the TUI | The error has no workflow-owned durable record |
| Plugin `build_runner()` | A handle may exist, but its context is still `None` | `save_checkpoint()` rejects context-less checkpoints |
| Phase/provider/tool error | Some runners save a terminal `failed` checkpoint | Recovery intentionally excludes terminal failed records |
| `asyncio.TimeoutError` in `run_turn()` | The TUI closes the turn but does not invoke workflow failure handling | The lifecycle and checkpoint remain stale or running |
| Cancellation without an explicit pause | Several paths mark `failed` and swallow save errors | An interrupt can destroy a safe continuation point |
| Resume-continuation exception | TUI and runner paths can both finalize the same failure | State transitions and checkpoint writes are duplicated and race-prone |
| Checkpoint validation/codec/write error | Some errors disable checkpoint support or are swallowed | The UI can claim failure was handled although no durable state exists |
| Error during initial setup | The typed context is created inside `run()` | A recoverable failure can happen before serializable state exists |

The exact names may evolve during implementation, but the ownership boundary
must remain the one described in `AGENTS.md`: `TUISession` coordinates
interactive execution, the workflow handle owns run lifecycle, the checkpoint
store owns durable bytes and claims, and workflow runners own typed phase state.

### 1.2 Existing lifecycle mismatch

The current checkpoint lifecycle includes `running`, `pausing`, `paused`,
`resuming`, `complete`, `failed`, and `discarded`. The recovery coordinator
considers `running`, `pausing`, `paused`, and `resuming` recoverable, while
`failed` is terminal by design. That distinction is correct for invariant
violations and corrupt state, but it is wrong for a transient provider error,
timeout, tool failure, or ordinary phase exception when the context is valid.

The implementation must therefore distinguish:

1. a recoverable error that pauses a valid workflow context; and
2. a terminal failure for which resuming would be unsafe or impossible.

The recommended compatibility-preserving representation is to keep the
workflow lifecycle `paused` for recoverable errors and add an explicit
`pause_reason`/`failure_kind` field. `failed` remains terminal for
non-recoverable failures. This avoids requiring every existing lifecycle
consumer to understand a new status while making the user-visible disposition
unambiguous.

## 2. Problem statement

The workflow engine currently has multiple error owners. A runner may catch an
exception, `TUISession` may catch the same exception, and cleanup may attempt a
third terminal transition. Each layer makes a locally reasonable decision,
but there is no idempotent coordinator that guarantees the following invariant:

> Before a workflow error is reported as handled, its latest safe state and
> error disposition are durably recorded, or a durable diagnostic explains why
> recovery is impossible.

The absence of that invariant causes four user-visible defects:

- an error can erase the only in-memory handle before it is saved;
- a valid workflow can be classified as terminal and disappear from resume;
- a timeout can return without changing workflow state at all; and
- a checkpoint failure can be hidden behind a generic error notification.

## 3. Goals

- Save or durably diagnose every workflow error, including setup, phase,
  provider, tool, timeout, cancellation, resume, and cleanup failures.
- Make transient or otherwise safe workflow errors resumable from the last valid
  typed context and phase boundary.
- Preserve the existing `run_id`, `conversation_id`, intent, artifacts,
  approval state, phase history, cache metadata, and workspace/provider
  identity.
- Resume the exact run rather than silently starting a new run or phase one.
- Ensure one idempotent failure-finalization path is used by TUI and runners.
- Keep checkpoint writes atomic, bounded, revisioned, redacted, and compatible
  with PRD-169 tool-call transaction repair.
- Make workflows produced by `create_workflow` satisfy the same contract by
  construction.
- Preserve backwards compatibility for existing valid checkpoints and custom
  workflow plugins where safe.

## 4. Non-goals

- Rolling back an external side effect that completed before the error.
- Replacing lauren-ai's agent-turn or tool-executor implementation.
- Auto-running a workflow merely because an error checkpoint is discovered.
- Reconstructing provider history from rendered TUI state.
- Persisting credentials, live clients, asyncio primitives, browser objects, or
  arbitrary Python objects.
- Making an unsafe or corrupt context resumable just to improve UX.
- Weakening workspace, network, browser, MCP, or command security policy.

## 5. Proposed product contract

### 5.1 Error classification

Every workflow error is normalized into a bounded, serializable record with a
stable kind, safe message, phase location, and recoverability disposition.

Minimum error kinds:

| Kind | Examples | Default disposition |
|---|---|---|
| `provider_transient` | timeout, rate limit, transport interruption, temporary provider failure | `paused`, resumable |
| `tool_transient` | tool timeout, unavailable MCP/browser service, recoverable subprocess failure | `paused`, resumable |
| `phase_execution` | ordinary exception while executing a phase | `paused` if context validates |
| `user_cancelled` | cancellation not accompanied by a deliberate reset | `paused`, resumable |
| `process_interrupted` | stale `running`/`resuming` checkpoint found after restart | `paused`, resumable after validation |
| `configuration` | invalid provider/profile/workspace configuration | `paused` if the context is valid; otherwise diagnostic-only |
| `checkpoint_serialization` | unsupported context, invalid payload, size limit | terminal, diagnostic-only |
| `checkpoint_storage` | permission, disk, atomic-replace, or corruption failure | terminal, diagnostic-only unless a fallback record is written |
| `workflow_invariant` | invalid transition, mismatched run ID, impossible phase topology | terminal, diagnostic-only |
| `plugin_incompatible` | missing plugin, fingerprint mismatch, incompatible schema | terminal, diagnostic-only |

The classifier must not expose raw secrets, authorization headers, full
prompts, tool arguments, or unbounded exception text. It may retain a bounded
exception type and sanitized message for diagnostics.

### 5.2 Recoverable error state

A valid workflow context that fails during an operation enters:

```text
handle.lifecycle = "paused"
handle.pause_reason = "workflow_error" | "timeout" | "tool_error" | ...
handle.failure_kind = <stable kind>
handle.last_error = <bounded safe diagnostic>
```

The checkpoint is written with the latest safe context and a monotonic
revision. The recovery coordinator must list it as recoverable and expose the
reason to the TUI. The user can resume the same `run_id` after correcting the
underlying condition.

The workflow must not be marked `complete` after a runner returns if a failure
was recorded during that run. A normal return is only completion when the
runner explicitly reports a valid terminal success state.

### 5.3 Non-recoverable error state

An error is terminal only when the framework cannot safely restore the context,
cannot establish the run identity, or detects an invariant/storage failure
that makes continuation unsafe. The system must persist a diagnostic record
where possible and display an explicit message that the run is not resumable.

Terminal failure must never be used as a generic substitute for an ordinary
phase or provider exception merely because an error was raised.

### 5.4 Initial run bootstrap

The framework must establish a durable workflow identity and a serializable
initial context before executing failure-prone plugin setup or the first agent
turn. The implementation should add a plugin/runner initialization contract,
for example:

```python
initial_context = plugin.create_initial_context(
    intent=intent,
    run_id=run_id,
    session_memory=session_memory,
)
```

The exact API may differ, but it must provide the following guarantees:

- the `run_id` and claim exist before provider/tool/phase execution;
- the context contains the original intent and initial phase state;
- the context can be encoded by the plugin checkpoint codec;
- `build_params()` and `build_runner()` failures can be associated with that
  run; and
- the initial checkpoint is written before the first agent request.

If a legacy plugin cannot construct a valid context, the framework must write
the diagnostic fallback described below and explicitly mark the run
non-resumable. It must not claim that the workflow was saved for resume.

### 5.5 One failure finalizer

Introduce one idempotent failure finalization operation at the workflow
coordination boundary. It may be a dedicated
`WorkflowFailureCoordinator`, a method on `WorkflowRunHandle`, or a similarly
named owner, but all paths must use the same operation:

- phase/provider/tool exception;
- `asyncio.TimeoutError` from `run_turn()`;
- cancellation without an explicit pause request;
- exception while building params or the runner;
- exception from `runner.resume()`;
- session shutdown and cleanup;
- checkpoint save/codec failure handling.

The finalizer must:

1. atomically claim finalization for the run so duplicate handlers are no-ops;
2. classify and sanitize the error;
3. capture the latest valid context and safe phase location;
4. choose recoverable `paused` or terminal `failed` disposition;
5. persist the checkpoint or a durable fallback diagnostic;
6. emit one structured workflow outcome event; and
7. release the workflow claim only after durable persistence is complete.

It must be safe to call from both a runner and `TUISession`. Runners may
contribute context and classification details, but they must not independently
perform competing terminal transitions.

### 5.6 Timeout and cancellation semantics

Workflow timeouts must flow through the failure finalizer. A timeout must not
only close the conversation turn while leaving the workflow `running`.

An Esc pause remains an intentional pause and keeps its existing
`user_interrupt` reason. A cancellation caused by shutdown, task cancellation,
or an unexpected transport interruption becomes `paused` when a valid context
exists. A deliberate `/workflow reset` remains destructive and produces the
existing `discarded` disposition after the user action is confirmed.

### 5.7 Checkpoint-write failure semantics

Checkpoint errors must not be silently converted into “handled” workflow
errors. If the primary checkpoint cannot be written, the framework must:

- retain the in-memory handle until finalization is complete;
- emit a structured diagnostic with the run ID and safe error kind;
- write a bounded fallback record when the filesystem permits it; and
- tell the user whether resume is possible.

If neither the typed checkpoint nor fallback record can be persisted, the UI
must say that the run's recovery state could not be saved and include the
non-secret run ID. Claim release and handle clearing must follow the explicit
failure policy, not happen silently in a generic `finally` block.

### 5.8 Resume behaviour

`/workflow resume [run-id]`, `agenthicc --resume`, and `--continue` must use
the same recovery coordinator. An error-paused checkpoint must:

- be discoverable by `inspect()`;
- pass plugin, schema, workspace, provider-profile, conversation-cursor, and
  PRD-169 tool-tail validation;
- be claimed by one live owner;
- restore the same `conversation_id` and session memory;
- restore the exact typed phase state and artifacts; and
- call the runner's true `resume(context)` method.

After resumption, a new error must create another paused checkpoint for the
same run with a higher revision. It must not create a new workflow run or call
`run(original_intent)` as a resume fallback.

### 5.9 User experience

After a recoverable failure, the TUI must display a concise notification such
as:

```text
Workflow 'name' paused after a provider timeout in phase 'phase'.
Run <run-id> is saved. Fix the issue, then use /workflow resume <run-id>.
```

The run ID, workflow name, phase, error category, and resumability must be
visible. Raw traceback text must remain in diagnostics/logs subject to the
existing redaction policy. If resume is unavailable, the notification must
say why and suggest reset or manual recovery.

The recovery list must distinguish:

- paused after user interrupt;
- paused after workflow error;
- interrupted by a previous process; and
- terminal failure that is retained for diagnosis but not resumable.

### 5.10 Generated workflows

`create_workflow` must make the contract automatic for downstream users:

- generated workflows have a serializable typed context or use the framework's
  declarative context codec;
- initial context creation happens before the first provider/tool call;
- phase methods preserve artefacts, phase history, approval state, and the last
  safe transition;
- the runner delegates failure finalization to the framework wrapper;
- `resume(context)` restores state and continues at the exact phase;
- generated code never catches an exception and marks the run complete;
- generated code never implements resume as a fresh `run(intent)` call; and
- generated system prompts and authoring tools explicitly instruct the agent
  to ask the user clarifying questions when required, preserve checkpoint
  state, and make external side effects idempotent or receipt-backed.

The `create_workflow` design, generation, and validation phases must inspect
the generated module for these requirements. Validation must reject a custom
runner that can execute a phase before context initialization, has no usable
checkpoint codec, swallows failures, or has a resume path that restarts the
workflow.

## 6. Data model and persistence changes

### 6.1 Checkpoint fields

Extend the existing checkpoint model with optional, versioned fields:

```text
pause_reason: "none" | "user_interrupt" | "workflow_error" |
              "timeout" | "tool_error" | "process_interrupted" |
              "configuration_error"
failure_kind: string | null
failure_message: bounded sanitized string | null
last_safe_boundary: string | null
error_revision: non-negative integer
```

`failure_message` is diagnostic text, not a transcript. It must be bounded and
redacted before persistence. Existing `reason` remains readable for backward
compatibility; new writes should use the structured fields as the source of
truth.

Existing schema-version-1 checkpoints must load with defaults equivalent to
`pause_reason="none"`, `failure_kind=null`, and `error_revision=0`. A schema
version bump is appropriate if required by the implementation, but migration
must be explicit and one-way safe. Unknown optional fields must not break old
valid checkpoints.

### 6.2 Fallback recovery envelope

Add an atomic, permission-restricted fallback record for failures that happen
before typed context creation or prevent a full checkpoint. A suggested path is
inside the existing run directory:

```text
<session>/workflows/<run-id>/recovery-error.json
```

It contains only:

- run ID, session ID, workflow name, and plugin fingerprint;
- creation/update timestamps and record revision;
- original intent in a bounded, redacted form or a safe intent digest;
- phase name/index if known;
- failure kind and sanitized diagnostic;
- whether a typed checkpoint exists and whether resume is possible.

This envelope is a durable diagnostic, not a substitute for a typed context.
It must never be presented as resumable when the context cannot be restored.
The store must use the same path validation, atomic replacement, file mode,
size bound, and directory durability rules as the primary checkpoint store.

### 6.3 Recovery records

`WorkflowRecoveryRecord` must expose the structured failure disposition so the
TUI and CLI do not infer meaning from a free-form string. Recoverable error
pauses remain `recoverable=True`; fallback-only records are visible as
`diagnostic_only=True` and are excluded from resume selection.

The implementation must preserve the ownership boundaries in `AGENTS.md` and

## 8. Data flow

### 8.1 New-run flow

```text
user message
  -> TUISession resolves workflow/plugin
  -> allocate run_id and workflow claim
  -> create initial typed context
  -> write checkpoint(status=running, context=initial)
  -> construct params/runner
  -> enter phase and persist phase boundary
  -> run agent/tool turn using the existing session conversation_id
```

### 8.2 Recoverable failure flow

```text
provider/tool/phase/timeout/cancellation exception
  -> common failure finalizer (idempotent)
  -> classify + redact error
  -> capture latest valid context and safe phase boundary
  -> checkpoint(status=paused, pause_reason=<kind>, context=<state>)
  -> emit one structured event and TUI notification
  -> retain durable run record; release live claim
  -> user fixes cause and invokes /workflow resume <run-id>
  -> recovery validates checkpoint and repairs tool tail
  -> claim run and restore same conversation_id/context
  -> runner.resume(context)
```

### 8.3 Pre-context or persistence failure flow

```text
setup/context/checkpoint failure
  -> common failure finalizer
  -> write typed checkpoint if possible
  -> otherwise atomically write recovery-error.json
  -> mark diagnostic_only=true, resumable=false
  -> display exact reason and safe run_id
  -> never advertise /workflow resume for an unrehydratable run
```

### 8.4 Repeated failure flow

```text
same run_id, revision N, resume
  -> exact phase/context restored
  -> next error
  -> paused checkpoint revision N+1
  -> no duplicate run, no phase-one restart, no duplicate committed tool effect
```

## 9. Functional requirements

### FR-1 — Durable run bootstrap

The framework shall create the run identity, claim, initial serializable
context, and initial checkpoint before any failure-prone provider, tool, or
phase operation. Setup failures shall be associated with that run.

### FR-2 — Central failure finalization

All workflow error paths shall call one idempotent finalization operation. A
second caller shall observe that finalization is already committed and shall
not write a conflicting status, emit a duplicate outcome, or release another
owner's claim.

### FR-3 — Recoverable phase errors

When typed context and checkpoint persistence are valid, provider, tool,
timeout, ordinary phase, and unexpected cancellation errors shall produce an
error-paused checkpoint containing the last safe state.

### FR-4 — Explicit terminal failures

Serialization, storage, plugin identity, schema, invariant, and invalid
context failures shall be terminal or diagnostic-only. The UI and recovery
coordinator shall clearly distinguish them from resumable error pauses.

### FR-5 — Timeout coverage

Every workflow timeout path, including the `run_turn()` timeout wrapper, shall
persist a workflow disposition before the turn is closed and the handle is
cleared.

### FR-6 — Checkpoint error visibility

The system shall never silently swallow a checkpoint failure. It shall attempt
the fallback envelope and expose whether recovery is available.

### FR-7 — Exact resume

Resuming an error-paused run shall use its existing run ID, session
conversation ID, typed context, phase index, iteration, artefacts, and tool
transaction cursor. It shall invoke `resume(context)` and never silently call
`run(original_intent)`.

### FR-8 — Safe claim lifecycle

The run claim shall remain held while finalization writes durable state and
shall be released exactly once afterward. A failed cleanup must not delete or
overwrite another live owner's checkpoint.

### FR-9 — Structured diagnostics

Workflow outcome events, recovery records, logs, and TUI notifications shall
include a stable safe error kind, run ID, workflow, phase, revision, and
resumability. Secrets and unbounded model/tool content shall be excluded.

### FR-10 — Recovery discovery

The recovery coordinator and session startup shall discover error-paused
checkpoints after process restart. `--continue`, `--resume`, and
`/workflow resume` shall share the same validation and selection logic.

### FR-11 — Generated-workflow enforcement

`create_workflow` shall generate and validate workflows that initialize context
early, persist checkpoint-compatible state, delegate error finalization, and
resume at the exact phase. Invalid generated custom runners shall be rejected
before publication.

### FR-12 — Backwards-compatible migration

Existing valid checkpoint files shall remain loadable. Old checkpoints without
failure metadata shall retain their current lifecycle meaning and receive
safe defaults. Existing valid built-in and custom workflows shall continue to
run, with a clear diagnostic for plugins that cannot meet the new recovery
contract.

## 10. Testing strategy

Tests must be deterministic, isolated, and use temporary session/workflow
stores. External providers, subprocesses, browsers, MCP servers, and clocks
must be faked or controlled.

### 10.1 Unit tests

Add coverage for:

- setup failure in `build_params()` after run bootstrap;
- handle claim failure and duplicate finalization;
- `build_runner()` failure before and after context attachment;
- initial-context codec rejection and fallback-envelope creation;
- provider, tool, phase, timeout, and cancellation classification;
- recoverable error pauses versus terminal invariant failures;
- timeout routing through the common finalizer;
- checkpoint save failure, size failure, permission failure, and fallback
  persistence;
- monotonic revisions and atomic status ordering;
- bounded/redacted diagnostic payloads;
- old checkpoint migration and unknown optional fields;
- `WorkflowRecoveryRecord` recoverability and diagnostic-only semantics;
- exact `resume(context)` dispatch and rejection of fresh-run fallback;
- repeated error → resume → error transitions;
- claim release exactly once and no duplicate error events.

### 10.2 Integration tests

Add tests that exercise the real TUI/session/workflow/checkpoint boundaries for:

- an error in every built-in workflow phase;
- provider timeout and transient provider failure;
- tool/MCP/browser failure and PRD-169 interrupted tool-tail repair;
- an exception during workflow construction;
- process restart with `running` or `resuming` state;
- error-paused checkpoint loaded by `--resume` and `/workflow resume`;
- same session memory and conversation ID before and after resume;
- multiple recoverable runs and explicit run selection;
- stale owner claims, duplicate recovery attempts, and release after error;
- corrupt primary checkpoint with a valid fallback diagnostic;
- inaccessible store where the UI reports that recovery could not be saved;
- repeated pause/resume/error cycles without a new run ID or duplicate tool
  side effect.

### 10.3 End-to-end tests

Cover these user journeys:

1. Start a multi-phase workflow, force a provider error, observe “saved and
   paused,” fix the provider, run `/workflow resume <run-id>`, and verify that
   execution continues in the failed phase with prior artefacts intact.
2. Start a workflow, terminate the process during a phase, launch with
   `agenthicc --resume <session-id>`, select the interrupted run, and resume
   without a new workflow.
3. Cause a timeout and verify it cannot leave the TUI in a false idle state or
   an unrecoverable `running` checkpoint.
4. Cause a pre-context setup error and verify a diagnostic-only record and an
   actionable non-resumable message.
5. Generate a custom workflow through `create_workflow`, inject errors into
   every generated phase, and verify checkpoint-aware resume for each one.
6. Resume the same run twice with an error on each attempt and verify
   monotonic revisions, one owner, one conversation, and no duplicate writes.

## 11. Non-functional requirements

### Durability and consistency

- Primary and fallback records use atomic replacement, restricted permissions,
  bounded size, and directory durability consistent with the current store.
- A status/event claiming that a run is saved is emitted only after the bytes
  are durably written.
- Checkpoint revisions are monotonic and stale writers cannot overwrite newer
  state.
- Finalization is idempotent across cancellation, timeout, runner, and TUI
  cleanup races.

### Security and privacy

- Do not persist API keys, authorization headers, cookies, provider secrets,
  raw tool arguments, full prompts, or arbitrary exception payloads.
- Apply existing path validation, workspace policy, and claim ownership checks
  to fallback records.
- Treat fallback JSON as untrusted input during recovery and validate every
  field before display or use.

### Performance

- Checkpoint encoding and failure metadata must add no provider round trip.
- Normal checkpoint overhead must remain bounded and must not block the TUI
  event loop longer than the existing checkpoint-store contract permits.
- Diagnostics must be compact; large phase artefacts remain subject to the
  existing checkpoint size policy rather than being duplicated in error files.

### Maintainability

- Keep lifecycle transitions and persistence in the existing workflow handle,
  store, recovery, and runner ownership boundaries.
- Use typed error/disposition models rather than free-form string parsing.
- Document public contracts in the workflow guide and generated-workflow
  authoring guidance when implementation begins.

## 12. Acceptance criteria

- [ ] Every workflow error path has a tested call to the common finalizer.
- [ ] A failure after context initialization produces a durable `paused`
      checkpoint with structured reason and a valid recovery record.
- [ ] A workflow timeout cannot leave a workflow falsely `running` without a
      checkpoint or fallback diagnostic.
- [ ] Setup failures before the first agent turn produce a saved run record;
      when no valid context exists, the record is explicitly diagnostic-only.
- [ ] `/workflow resume <run-id>` discovers and resumes an error-paused run
      after a process restart.
- [ ] `--continue` and `--resume` use the same recovery validation and retain
      the original `conversation_id`.
- [ ] Resume restores the exact phase, typed state, artefacts, approvals,
      iteration, and cache metadata.
- [ ] No resume path invokes a fresh `run(intent)` fallback for a recoverable
      typed context.
- [ ] A second failure on a resumed run pauses the same run with a higher
      revision and does not duplicate committed tool side effects.
- [ ] Checkpoint failures are visible, redacted, and represented by a fallback
      diagnostic when possible; no code silently advertises a saved run.
- [ ] `create_workflow` generated workflows pass initialization, codec, error,
      and true-resume validation and include user-question guidance.
- [ ] Existing schema-version-1 valid checkpoints load and behave as before.
- [ ] Unit, integration, and E2E tests cover all failure classes and pass in
      isolated CI execution.

## 13. Rollout and compatibility

Implement the change in this order:

1. Add typed failure/disposition models and checkpoint migration.
2. Add the fallback envelope and store tests.
3. Introduce the idempotent finalizer and route TUI timeout/cancellation/setup
   paths through it.
4. Update runners and built-in contexts to initialize early and report safe
   boundaries.
5. Update recovery discovery, command UX, and resume selection.
6. Update `create_workflow` prompts, tools, generated templates, and static
   validation.
7. Run the complete unit/integration/E2E matrix and document the resulting
   evidence.

Existing terminal `failed` checkpoints must remain inspectable and must not be
silently converted to resumable state. New error-paused records use the
existing `paused` lifecycle plus structured metadata, so clients that only
understand lifecycle values continue to render them as paused. Clients that
understand the new fields can explain why the pause occurred.

## 14. Assumptions and open implementation decisions

- This PRD selects `paused + pause_reason/failure_kind` rather than adding a
  new lifecycle literal, minimizing compatibility risk with existing stores,
  reducers, and TUI renderers.
- A fallback envelope is diagnostic-only. True resume requires a validated
  typed context; the implementation must not fabricate one from an error
  message.
- The framework may provide a default generic initial context for declarative
  workflows, while custom workflows must provide a codec or be rejected as
  non-resumable.
- External effects are protected through existing tool/process idempotency and
  receipt contracts; this PRD does not promise rollback.
- If a primary checkpoint write fails because of a transient filesystem error,
  a later explicit recovery/repair command may retry it, but the first error
  must still be surfaced and recorded as far as the filesystem permits.

## 15. Definition of done

This PRD is complete when all acceptance criteria are checked, the documented
data flow is implemented across the TUI, workflow handle, checkpoint store,
recovery coordinator, and runners, generated workflows are validated against
the same contract, and the complete deterministic test matrix passes without
known regressions.

## 16. Implementation and verification evidence

The implementation uses the existing ownership boundaries: `TUISession` and
the headless runner coordinate execution, `WorkflowRunHandle` owns lifecycle
and failure finalization, `WorkflowCheckpointStore` owns atomic bytes and
claims, and `WorkflowRecoveryCoordinator` owns fail-closed discovery and
rehydration. `WorkflowPlugin.create_initial_context()` establishes the early
context hook used by both interactive and headless startup. Built-in runners
retain their local failed projection for state-machine diagnostics but leave
workflow-handle error disposition to the common finalizer; generated custom
runners are statically rejected when they terminalize ordinary failures or
restart from `run()` during resume.
