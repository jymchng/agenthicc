# PRD-166 — Terminal-Safe Active Animation Rendering

## 1. Executive summary

While an agent is actively thinking, agenthicc intentionally advances the
flower and Thinking animation on every session tick. The workspace sends each
new frame to Rich `Live`, which normally replaces the previous Live surface by
emitting cursor movement and erase controls.

Some terminal clients, transcript viewers, logging adapters, and captured
consoles do not execute those controls. They treat every replacement as
append-only text. The result is a visible sequence such as:

```text
✾ Thinking │ 37m 23s │ ↑ ...
openai/agnes-2.0-flash
❋ Thinking │ 37m 23s │ ↑ ...
openai/agnes-2.0-flash
✽ Thinking │ 37m 23s │ ↑ ...
openai/agnes-2.0-flash
❊ Thinking │ 37m 24s │ ↑ ...
openai/agnes-2.0-flash
```

This is not duplicate LLM output, duplicate workflow execution, or duplicate
conversation history. It is one initial Live render plus active animation
frames displayed as ordinary output. The flower sequence proves that the
frames are being generated by `StatusComponent` from `ConversationStore.frame`.

PRD-164 suppresses frame publication for static idle states. PRD-165
suppresses timer-driven redraws while approval and question prompts own the
terminal. This PRD addresses the remaining case: active animation is valid in
an ANSI replacement terminal but unsafe in an append-only output target.

The solution is a capability-aware workspace render policy. Interactive
replacement terminals retain the current animation. Append-only or unknown
targets use a snapshot-safe policy that ignores frame and timer-only redraws
and renders the current status only at meaningful state boundaries.

## 2. Exact problem statement

### 2.1 Current data flow

```text
TUISession._tick()                          every 50 ms
        │
        ▼
ConversationStore.tick()
        │
        ├─ display/activity timing signal changes
        └─ frame.set(frame + 1)
                │
                ▼
Workspace frame/timing subscriptions
        │
        ▼
Workspace._redraw()
        │
        ▼
Live.update(_build(), refresh=True)
        │
        ├─ flower changes: ✾ → ❋ → ✽ → ❊ → ✿
        ├─ Thinking text is re-rendered
        └─ model/tokens/status surface is re-rendered
        │
        ▼
Append-only or ANSI-insensitive client
        └─ every replacement becomes visible history
```

### 2.2 Current ownership

| Concern | Current source | Finding |
|---|---|---|
| Session tick | `src/agenthicc/runners/tui_session.py` | Calls `ConversationStore.tick()` every 50 ms. |
| Animation counter | `src/agenthicc/tui/conversation_store.py` | Advances during thinking, tool execution, recovery, and compaction. |
| Status animation | `src/agenthicc/tui/workspace/components.py` | Maps `frame % 8` to the flower and animates the Thinking word. |
| Live subscription | `src/agenthicc/tui/workspace/workspace.py` | Subscribes frame and timing signals to redraw callbacks. |
| Live replacement | `Workspace._flush_redraw()` | Calls Rich `Live.update(..., refresh=True)`. |
| Durable conversation | `ConversationStore` events/session logs | Not involved in the repeated snapshots. |

### 2.3 User impact

- Captured output is flooded with transient status frames.
- Long-running agents appear to repeat output even though the model is making
  one uninterrupted turn.
- Hosted TUI clients may show dozens or hundreds of redundant status panels.
- The output becomes difficult to scroll, search, or use as a transcript.
- The session performs unnecessary rendering and terminal writes when the
  output target cannot replace the previous surface.

### 2.4 Reproduction

The issue is deterministic without a provider or network call:

1. Create an `AppState` and begin one conversation turn.
2. Set a model, session ID, and token counters.
3. Start a `Workspace` with a recording `Console` configured with terminal
   output capture.
4. Run five active ticks and yield to the event loop after each tick.
5. Stop the workspace and count `Thinking` or model lines in the captured
   output.

The current behavior produces one initial status snapshot plus one snapshot
per active frame update. The final `frame` value is five after five ticks.

## 3. Goals

1. Preserve active flower/Thinking animation in terminals that can replace a
   Live surface.
2. Prevent active frame and timer ticks from appending duplicate status panels
   to append-only or ANSI-insensitive output targets.
3. Provide an explicit render capability/policy rather than guessing that all
   TTYs interpret Rich control sequences.
4. Make the default safe for non-interactive, captured, dumb, and unknown
   output targets.
5. Preserve meaningful redraws: state changes, tool changes, user input,
   notifications, model/token/cost changes, workflow progress, overlays,
   approvals, and terminal resize.
6. Preserve existing interactive animation timing and layout behavior.
7. Keep the fix within the current `Workspace`, `ConversationStore`, and
   terminal ownership boundaries.
8. Keep status rendering presentation-only; no conversation event or workflow
   checkpoint may be created for an animation frame.
9. Make the behavior observable through deterministic unit, integration, and
   end-to-end tests.

## 4. Non-goals

This PRD does not:

- remove active animation from a real interactive replacement terminal;
- change LLM requests, provider memory, workflow execution, or checkpoints;
- change the meaning of `ConversationStore.frame` for active animation;
- replace Rich Live with a new terminal framework;
- add a second transcript or conversation event stream;
- guarantee that arbitrary external clients understand ANSI controls;
- suppress legitimate status changes merely because output is captured;
- change headless approval, capability, sandbox, or security behavior;
- solve the separate idle-frame or approval-wait timer defects already covered
  by PRD-164 and PRD-165.

## 5. User-facing contract

### 5.1 Interactive replacement mode

When the output target declares that it can replace a Live surface:

- active frame updates continue at the existing cadence;
- flower and Thinking animation remain visible;
- Rich cursor and erase controls are used as today;
- timing, input, tool, workflow, and overlay redraws retain current behavior;
- idle and prompt-wait suppression from PRD-164 and PRD-165 remains active.

### 5.2 Append-safe snapshot mode

When the output target is append-only, captured, non-interactive, dumb, or
unknown:

- the workspace renders an initial current status surface;
- frame-only updates do not call `Live.update()`;
- timer-only updates do not call `Live.update()`;
- the latest status appears on the next meaningful state redraw or final
  completion redraw;
- no animation snapshot is written to the conversation event log;
- user input and meaningful state changes remain responsive according to the
  host client's rendering contract.

The append-safe mode intentionally sacrifices transient animation in exchange
for a usable, non-repeating transcript. It must never emit the same status
panel once per 50 ms tick.

### 5.3 Explicit override

The render policy must support an explicit override for hosted clients whose
TTY detection is misleading:

```text
auto              detect the safest supported policy
replace           force ANSI replacement/live animation
append_safe       suppress frame/timer-only redraws
```

The exact configuration surface may follow existing CLI/config conventions,
but the default must be `auto`, and `auto` must choose `append_safe` when
replacement capability cannot be proven.

## 6. Proposed solution

### 6.1 Add a render capability/policy owned by the workspace

Introduce a small typed policy in the existing TUI rendering ownership area,
for example:

```python
class LiveRenderMode(StrEnum):
    AUTO = "auto"
    REPLACE = "replace"
    APPEND_SAFE = "append_safe"
```

The policy resolver should consider, in order:

1. an explicit application/configuration override;
2. a client-provided render capability, if the hosting client exposes one;
3. Rich console terminal/interactivity information;
4. known unsafe conditions such as non-TTY output or `TERM=dumb`;
5. `APPEND_SAFE` as the conservative fallback.

The policy must be immutable for the lifetime of a `Workspace`. Changing it
mid-render would create another cursor-ownership race.

The policy is a rendering capability, not a security setting. It must not
affect tools, approvals, network access, sandbox scope, or workflow behavior.

### 6.2 Separate redraw reasons

The workspace must treat these as distinct redraw reasons:

| Reason | Replace mode | Append-safe mode |
|---|---:|---:|
| Active animation frame | redraw | suppress |
| Active timing tick | redraw | suppress |
| Idle/complete/error timer tick | suppress | suppress |
| Input edit/cursor | redraw | redraw according to host contract |
| Tool/state transition | redraw | redraw |
| Tokens/cost/model change | redraw | redraw |
| Workflow/notification change | redraw | redraw |
| Approval/question transition | redraw | redraw |
| Terminal resize | one geometry redraw | one explicit snapshot redraw |

The existing `_redraw_frame()` and `_redraw_activity()` callbacks should become
policy-aware. `display_elapsed_s` must not remain in an undifferentiated signal
list if doing so bypasses the append-safe timing guard.

### 6.3 Preserve the current active renderer

`REPLACE` mode must retain the current behavior rather than introduce a second
animation implementation. `ConversationStore.frame` remains the shared source
for flowers, Thinking text, and compaction spinners. The policy only decides
whether a frame notification reaches the Live replacement renderer.

### 6.4 Make AUTO conservative

`AUTO` must not assume that `isatty()` alone proves replacement support. A TTY
can still be proxied by a transcript viewer that displays raw writes. The
resolver should use the strongest available signal and fall back to
`APPEND_SAFE` when the capability is unknown.

If backwards compatibility requires keeping current TTY behavior, the policy
may initially select `REPLACE` for a positively identified interactive Rich
terminal and `APPEND_SAFE` for all other targets. Hosted clients should be able
to pass an explicit capability rather than relying on environment heuristics.

### 6.5 Meaningful snapshots in append-safe mode

Append-safe mode must not freeze the entire UI. It should still render on
semantic changes. The implementation must ensure that:

- a Thinking state transition renders the current status at least once;
- a tool start/completion can render its current status;
- a new assistant/user/system event remains visible through the existing
  scroll-buffer path;
- a final completion or error renders the terminal status once;
- a resize can refresh the current geometry once;
- frame and timing ticks alone do not render.

If the host is truly append-only, semantic redraws may still appear as
separate snapshots; that is acceptable because they correspond to actual
state changes, not an animation clock.

### 6.6 No durable side effects

The policy must never append `ConversationEvent` records, modify session logs,
write checkpoints, or alter provider memory. A frame is a presentation signal
only.

## 7. Functional requirements

### FR-166.1 — Policy resolution

The workspace MUST resolve one immutable render mode from explicit override,
client capability, terminal information, and conservative fallback.

### FR-166.2 — Interactive animation preservation

In `REPLACE` mode, active frame ticks MUST continue to redraw the flower,
Thinking text, recovery indicator, and compaction spinner.

### FR-166.3 — Append-safe frame suppression

In `APPEND_SAFE` mode, frame notifications MUST NOT call `Live.update()`.

### FR-166.4 — Append-safe timing suppression

In `APPEND_SAFE` mode, active `display_elapsed_s` and `activity_elapsed_s`
timer notifications MUST NOT call `Live.update()` unless accompanied by a
meaningful semantic state change handled by another signal.

### FR-166.5 — Meaningful redraw preservation

Input, tool, model, token, cost, workflow, notification, overlay, approval,
question, resize, completion, and error transitions MUST retain their current
redraw behavior in both modes.

### FR-166.6 — Default safety

`AUTO` MUST choose `APPEND_SAFE` when output replacement capability is unknown
or the output is non-interactive/captured.

### FR-166.7 — Explicit override

Users and hosting clients MUST be able to force `REPLACE` or `APPEND_SAFE`
without modifying workflow code or tool permissions.

### FR-166.8 — Lifecycle stability

The policy MUST remain stable across direct turns, workflows, compaction,
approvals, questions, interruption, resume, and completion.

### FR-166.9 — Persistence isolation

Animation and timer suppression MUST NOT add, remove, reorder, or duplicate
conversation events, session-log entries, workflow checkpoints, or memory
journal records.

### FR-166.10 — Backwards compatibility

Existing interactive terminals retain active animation by default when their
replacement capability is positively identified. Existing headless behavior
remains unchanged.

## 8. Non-functional requirements

- **Performance:** Append-safe mode performs no 20-Hz animation/timer Live
  updates. Replace mode retains current animation cost.
- **Portability:** POSIX, Windows, non-TTY, `TERM=dumb`, captured Rich
  consoles, and hosted clients have deterministic policy behavior.
- **Determinism:** Tests use controlled ticks and explicit policy values, not
  wall-clock sleeps or provider calls.
- **Maintainability:** No second source of truth for animation or workflow
  state is introduced.
- **Observability:** Optional diagnostics may report render mode and redraw
  reason, but must not log prompts, tokens, credentials, tool arguments, or
  conversation content.
- **Safety:** Render mode cannot bypass approvals, capabilities, sandboxing,
  or network policy.
- **Resource bounds:** Append-safe mode must not buffer unbounded historical
  Live snapshots in process memory.

## 9. Acceptance criteria

- **AC-166.1:** Five controlled active ticks in `REPLACE` mode produce changing
  flower/Thinking renders and preserve the current animation tests.
- **AC-166.2:** Five controlled active ticks in `APPEND_SAFE` mode produce zero
  frame-driven `Live.update()` calls after the initial render.
- **AC-166.3:** Captured output in append-safe mode contains one active status
  snapshot for a stable thinking interval, not one snapshot per frame.
- **AC-166.4:** The exact flower sequence `✾`, `❋`, `✽`, `❊`, `✿` remains
  available in replacement mode and is not appended in append-safe mode.
- **AC-166.5:** A real input edit, tool transition, token update, workflow
  progress change, notification, and completion still cause the expected
  redraw in both modes.
- **AC-166.6:** `AUTO` selects append-safe behavior for a captured/non-TTY or
  unknown replacement target.
- **AC-166.7:** Explicit `replace` and `append_safe` overrides are honored even
  when terminal auto-detection disagrees.
- **AC-166.8:** Resize produces one current geometry repaint and does not start
  an animation redraw loop in append-safe mode.
- **AC-166.9:** Direct turns, workflows, compaction, approval waits, question
  waits, interruption, resume, and completion preserve their existing state
  and persistence behavior.
- **AC-166.10:** Normalized captured output contains no duplicate frame-only
  status panels, and no new conversation events are persisted for frames.
- **AC-166.11:** Unit, integration, E2E, Ruff, formatting, type-audit, and
  applicable static checks pass without weakening existing baselines.

## 10. Test plan

### Unit tests

- render-mode resolution for explicit overrides, interactive terminals,
  non-TTYs, `TERM=dumb`, and unknown capabilities;
- frame redraw forwarded in `REPLACE` mode;
- frame redraw suppressed in `APPEND_SAFE` mode;
- timing redraw suppressed in `APPEND_SAFE` mode;
- semantic redraws forwarded in both modes;
- policy immutability after workspace startup;
- frame counter and status animation remain unchanged at the store level.

### Integration tests

- real `ConversationStore` and `Workspace` with five active ticks in each
  render mode;
- captured `Console` output and `Live.update` call counts;
- input, token, notification, workflow, approval, and completion redraws;
- terminal resize in both modes;
- no session-log, event, checkpoint, or memory writes from ticks;
- explicit policy propagation through TUI session construction.

### End-to-end tests

- long-running synthetic active turn in a captured console;
- Plan Review and Questions overlays while active animation is suppressed or
  replaced according to policy;
- workflow execution with progress and completion boundaries;
- interruption and resume without duplicate status history;
- a real replacement-capable terminal path retaining visible animation.

## 11. Rollout and compatibility

The default policy should initially be `AUTO`. Interactive terminals with a
positive replacement capability retain the existing behavior. Non-interactive,
captured, dumb, or unknown targets use append-safe behavior.

The policy should be released without a feature flag once captured-console and
interactive-terminal tests pass. A temporary diagnostic may report the chosen
mode and redraw reason, but it must be content-free and disabled by default.

No storage migration is required. Existing sessions and workflows resume with
the same provider memory, conversation events, and checkpoints.

## 12. Security and privacy

Render-mode selection is not a permission boundary. It must not change tool
availability, capability gates, approval requirements, workspace scope,
network guards, or secret handling. Diagnostics must not expose session
contents, prompts, token payloads, tool arguments, or credentials.

## 15. Open decisions

1. Whether the explicit override belongs in `[tui]`, a CLI flag, an
   environment variable, or all three through the existing configuration
   precedence rules.
2. Which client capability handshake is available to hosted front ends. The
   first implementation may use terminal detection plus explicit override.
3. Whether semantic snapshots in append-safe mode should be emitted through
   the existing Rich Live block or a future client-neutral status projection.

The recommended initial implementation is a workspace-local immutable policy,
with `AUTO` conservative for unknown targets and explicit overrides for hosted
clients.
